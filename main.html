GIT WORKFLOW PLAYGROUND / GH STACK

Learn stacked pull requests by doing.

Build a stack, navigate between dependent branches, rebase lower layers, and merge a stack. The branch stack, commit graph, and simulated terminal update as you experiment. No GitHub account or repository access is needed.

Build your first stack

Create a chain of dependent branches one layer at a time.
You can also type commands in the terminal. Try gh stack init feature-auth feature-api feature-ui to create three layers in one step, and git commit to add a commit on the checked-out branch.
CI on a stack. GitHub evaluates every PR in a stack as if it targets the stack base (usually main), not the branch below it. A workflow that runs on pull_request events targeting main therefore runs for every PR in the stack, not only the bottom one, and required status checks must pass on every PR below a PR before it can merge. Watch the CI runs started counter: submitting three PRs starts three runs, and a rebase gives the rewritten branches new commits, so their checks run again when you push. See Optimizing CI for stacked pull requests.

Navigate & rebase

Navigation changes HEAD; rebasing updates branch ancestry.

Move through the stack. up moves away from trunk toward the top; down moves toward trunk.

Try a cascading rebase. Add a commit to the bottom branch. The simulator checks out that branch, then gh stack rebase --upstack replays the branches above it onto its new tip.

A branch no longer starts at its parent's tip. Run a rebase from the changed branch up through the top of the stack.

Trunk moved ahead. Commit on main, as if a teammate's work landed there. Every branch now starts at an older main commit, so the stack loses its linear history. gh stack rebase fetches the trunk and replays the stack onto it; gh stack push then updates the PRs.

Merge a stack

Choose a PR; its unmerged dependencies below it are included.

Merging through PR #2 merges PR #1 and PR #2 together. PRs above #2 remain open. In the real CLI the merge set is all-or-nothing: if any PR can't merge, none do. GitHub checks each PR against the rules for the stack base, so every PR up to the one you pick needs passing required checks and a linear history.

What the method changes. Squash lands one new commit per PR, and rebase replays the commits with new SHAs, so the original commits disappear from main and the branches above must be rebased. A merge commit keeps the original commits, so the branches above still start from commits that exist on main and have nothing to replay.
This tab demonstrates merge scope. It does not call GitHub or merge a real pull request.

Rebase conflicts

A conflict pauses the rebase; you either finish it or put everything back.

Build a stack with at least two branches and submit it, then create a conflict: add a commit that edits the same line your stack edits, and run gh stack rebase. The rebase stops on the first branch that cannot be replayed cleanly. Resolve the file, stage it with git add, then run gh stack rebase --continue. Or run gh stack rebase --abort to restore every branch to its state before the rebase. While a rebase is paused, other stack commands are blocked.

gh stack sync reacts differently: on a conflict it restores every branch and tells you to run gh stack rebase to resolve it interactively. gh stack init also enables git rerere, so a resolution Git has seen before is reused on later rebases (not simulated here).
